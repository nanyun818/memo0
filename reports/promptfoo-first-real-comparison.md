## 唯一失败的含义

q10 的 baseline 回答“资料中没有提到 Mem0 的收入信息，无法回答”，supported=false，但 source_ids=["mem0"]。grounded 同样说明缺少收入信息，supported=false，source_ids=[]。

规则约定 source_ids 只列能支持实质答案的资料，资料不足时留空，因此 baseline 的引用字段被判失败。它没有编造收入金额，不能把该 FAIL 直接解释成事实错误或幻觉。若产品希望列出“检查过但不足以回答”的材料，可另加 consulted_sources，或修订引用语义并更新评分器；规则本身也需要符合产品需求。

两个检查中 JSON 检查通过、JavaScript 检查不通过，所以该输出聚合 score=0.5，但用例依然 FAIL。score 与“所有规则均通过”的 pass/fail 不同。

## 一个通过也没解决任务的例子

q05 两个 Prompt 均承认没有资料，规则检查通过。但用户仍没得到如何隔离项目依赖的方法。它验证了资料不足时的响应约定，端到端任务完成仍失败，首先检查关键词检索。规则通过率不能替代任务完成率。

## 表格怎么读

从左向右是 description（用例编号与类别）、question（题目）、context_text（实际提供资料），再到两套 Prompt 的输出。纵向每行一题，横向比较同题两个回答。Providers=1 表示一个模型接口，Tests=5 表示五道题，不代表只有五次调用。

2 PASS 表示两个检查通过，不是得到两分。Tokens 通常显示总量（输入+输出）；Latency 是单次请求延迟；Tokens/Sec 是速度；Cost 是框架按已知价格与用量估算的金额，实际费用看服务账单，不凭本页验证现行单价。

先看 Failures，再点放大镜看具体判分原因；切回 All 抽查通过项。Different 可用于找输出存在差异的行，不代表这些差异一定影响质量。搜索 q10 或其问题文字可快速定位。

本次明确指令改善了 q10 的引用约定遵循，规则通过数增加 1；其余四题规则结果相同。这只是五道开发题的一次观察，不证明 grounded 在全部问题上更强或具有 100% 事实准确率。下一步使用人工标准核对 PASS，并用语义反例验证规则漏检，再学习校准后的模型裁判。
