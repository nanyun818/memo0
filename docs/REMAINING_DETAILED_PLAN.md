## 项目主线与范围

建设一个“AI 学习与求职知识助手”：读取官方资料回答问题；说明依据；保存适合长期保留的偏好；必要时调用工具；通过固定评测检查质量并展示日志。场景首先是课程设计假设，需经过试用验证。

深度主线：Python/API、promptfoo + Python 应用评测、RAG、Mem0、一个工具调用流程、产品需求与实验报告。其他项目做边界明确的小实验：Ragas 指标、Langfuse 记录、lm-evaluation-harness 小样本任务、Inspect AI 工具评测、OpenViking 最小示例、Harness² 演示、Dream-RSI 方法和有限改进实验。全部生产级掌握不适合作为剩余 50 小时的承诺。

现状：服务器与 API 已运行；会话与持久化有示例；promptfoo 五题两 Prompt 的真实对照已验证，普通指令 4/5、强调依据指令 5/5，差异在引用约定。模型裁判已准备、离线检查通过，真实裁判与学习者独立评分待完成。尚未完成向量 RAG、Mem0 或这些研究框架的真实实验。

## 每天共同的学习方式

每节开始附私人连接与环境命令。先讲本节在整个应用中的位置，用一个实际输入说明数据怎么走；再讲关键概念、运行最小实验、读关键代码、做一次独立修改、跑回归并提交。概念和执行结果分开验收，减少简单操作逐条截图。遇到不懂时回到具体题目，不继续堆新术语。

建议每 5 小时：45 分钟原理与图解，120 分钟实践，60 分钟读代码和独立修改，45 分钟评测/产品分析，30 分钟排障缓冲与 GitHub 记录。下面各天分配是工作预算；若当日未通过核心验收，先完成主线，扩展实验顺延并如实标注。

## 10/30：评测到底在检查什么（5h）

- 1h：用上一轮真实问题串起 Prompt、问题、资料、模型答案、程序规则与网页记录。
- 1.5h：先人工核对六条固定候选答案，再运行已部署的模型裁判，阅读中文理由。
- 1h：学习“依据一致性、事实正确性、任务完成度”的区别；检查规则引用约定是否符合产品意图。
- 1h：读 judge.yaml，独立改一个评分条件，保留版本并小规模比较，记录分歧而非迎合标签。
- 0.5h：缓冲与留痕。

验收：能解释“有资料但不能回答收入”的案例；能指出一个规则漏检；理解裁判可能错。交付：评分标准、六条标签的核对意见、真实裁判结果和分歧说明。不得把 AI 助教标签冒充人类独立标注。

## 10/31：Python 应用评测与 DeepEval（5h）

- 1h：拆解函数输入、返回值、list/dict、异常，读现有 API 调用和评分代码。
- 1.5h：独立环境安装兼容版本 DeepEval；将已有问题、上下文和固定答案转换成测试用例，先避免反复生成答案。
- 1h：运行一项明确的语义指标，比较程序断言、人工判分与模型裁判；区分指标阈值和通过率。
- 1h：机器学习入门：训练/开发/测试集、过拟合、损失与评测指标；独立修改一个用例并看到失败。
- 0.5h：缓冲与留痕。

验收：能运行单个 Python 测试，解释失败条件，知道当前没有在训练 DeepSeek。交付：测试代码、依赖版本、失败用例、测试集划分说明。官方入口：https://deepeval.com/docs/getting-started 。

## 11/01：把固定资料变成真正的检索流程（5h）

- 1h：理解文档、分块、Embedding、相似度、top_k、引用；区分检索与生成错误。
- 2h：准备约 10 份短官方资料，建立来源 ID；跑关键词基线；在核验资源后选择一个明确的 embedding 服务或小型本地模型，建立语义检索。DeepSeek 聊天接口不默认等于 embedding 接口。
- 1h：用“如何隔离项目依赖”等改写题对比，固定数据与生成模型，只改变检索方式。
- 0.5h：PRD 草稿：用户、核心任务、资料缺失时行为、验收标准。
- 0.5h：缓冲与留痕。

验收：新问题进入应用后会触发检索，而非在测试题内手写资料；至少解释一个改写题和一个误检题。交付：检索实现、资料来源、关键词/语义检索报告。改进没有发生时如实记录，不预填提升。

## 11/02：RAG 评测、Ragas 与 Langfuse（5h）

- 1h：读输入问题、检索片段、参考答案、实际答案四类字段，确定每个指标要什么数据。
- 1.5h：Ragas 先选一项检索指标和一项依据指标，跑少量已审核用例；补上参考标签，记录额外 LLM/embedding 用量。
- 1h：接入一个最小 Langfuse trace，关联一次检索与生成；优先评估托管服务或独立资源，当前小服务器不直接塞入完整重型栈。
- 1h：比较规则通过、任务完成、耗时和用量；选择一条失败进行修复，再做回归。
- 0.5h：缓冲与留痕。

验收：能区分“没找到资料”与“资料已给但回答错误”，能从 trace 找到一次调用。交付：指标配置、小样本报告、脱敏 trace 与修复记录。服务账号、数据上传范围和具体依赖到执行时确认；如果平台连接受阻，先保留本地完整日志，不把接入记为已完成。

## 11/03：长期记忆与 Mem0（5h）

- 1h：区分当前上下文、整段历史、外部知识库和用户长期记忆。
- 2h：核验 LLM、embedder、存储组件，在隔离环境使用 Mem0 库，实践保存、检索、更新、删除；先用虚构学习偏好。
- 1h：构造两个用户测试跨会话恢复、偏好更新、删除后不再检索、用户间不混用。明确应用中的身份归属，不把 user_id 当认证系统。
- 0.5h：产品规则：记什么、不记什么、用户如何查看和修改。
- 0.5h：缓冲与留痕。

验收：偏好跨会话可用、修改后用新偏好、删除可验证、另一个用户不能拿到它。交付：Mem0 示例、四类测试和记忆生命周期说明。官方入口：https://docs.mem0.ai/open-source/overview 。

## 11/04：把应用变成接口，并评测工具调用（5h）

- 1h：FastAPI、HTTP 请求/响应、参数校验，封装当前助手；只开放所需接口。
- 1.5h：增加一个可控工具，如查询学习资料或读取虚构任务清单；观察模型决定调用、程序执行和返回结果的过程。
- 1h：用 Inspect AI 最小任务记录可观察的工具调用；检查工具名、参数、调用次数、最终任务状态，限制步骤。
- 1h：SQLite 保存实验元数据，写基础 SQL 统计成功数、失败类型和平均耗时；确认失败数分母。
- 0.5h：缓冲与留痕。

验收：能画出一次工具执行流程，指出一次错误参数或不必要调用；工具成功执行不自动等于用户任务完成。交付：API 示例、工具与任务、轨迹评分脚本、SQL。官方入口：https://inspect.aisi.org.uk/ 。

## 11/05：论文 benchmark 与模型基础（5h）

- 1h：理解应用评测、模型基准、Agent 任务评测，以及 zero/few-shot、答案抽取、准确率和样本量。
- 1.5h：lm-evaluation-harness 核验接口与任务兼容性，选择支持的生成式任务跑约 10–20 个样本；资源/协议不支持则记录限制，不拿自定义测法冒充官方 benchmark。
- 1.5h：PyTorch 张量、梯度与一个微型训练练习；结合 Transformers 示例理解 tokenizer、输入、输出与推理。仅小规模 CPU 可行内容。
- 0.5h：读任务定义与模型接口文件，说明 generate_until 与 loglikelihood 的差别。
- 0.5h：缓冲与留痕。

验收：能说明测试协议为何影响分数，区分应用调参和更新模型权重。交付：版本、任务/样本数/参数、样例输出、基础模型实验。此阶段不承诺熟练 PyTorch/Transformers 或复现完整 MMLU。

## 11/06：OpenViking 与 Harness² 的最小实践（5h）

- 1h：比较 RAG、Mem0、OpenViking 解决的对象与边界，写选型表。
- 1.5h：核验 OpenViking 的依赖和 API，跑官方最小资源导入/检索示例，保留实际输出；不立即迁移主应用全部存储。
- 1h：Harness² 官方演示或最小可运行路径，观察任务如何执行与评分；核验当前 Python/工具依赖。
- 1h：源码走读任务、执行、评分入口，写一页结构说明；不能运行的部分记录具体依赖和阻塞，不称完整复现。
- 0.5h：缓冲与留痕。

验收：能说明为什么某个功能需要它，能展示最小结果或明确的可复核阻塞。交付：示例/依赖记录、源码卡片、选型表。Harness²：https://github.com/google-research/harness2 。lm-evaluation-harness 是另一个项目。

## 11/07：有限改进实验、Dream-RSI 与试用反馈（5h）

- 1h：阅读 Dream-RSI 的研究问题、反馈与改进循环、基准和限制，核验最小演示可行性。
- 1.5h：在我们的助手上做一次受控迭代：开发集定位失败 → 修改 Prompt/检索/工作流中的一个因素 → 固定回归 → 最后检查预留题。该实验只是应用改进练习，不冒充 Dream-RSI 研究复现或递归自我改进系统。
- 1h：整理 AgentBench 的环境、任务与评分思想，和我们的工具评测对照；不在本机部署全部基准环境。
- 1h：自己模拟一轮用户使用；有自愿试用者时收集反馈，整理需求、问题优先级与下一轮验证。没有真实试用者就标记模拟，不虚构访谈。
- 0.5h：缓冲与留痕。

验收：能说明改了什么、凭什么认为有改善、有哪些回退和不确定性。交付：实验报告、失败案例、反馈与优先级。Dream-RSI：https://github.com/google-research/dream-rsi 。

## 11/08：收尾、作品与求职材料（5h）

- 1h：从新终端按文档重现启动流程，核对依赖、接口、日志、结果和重启恢复。
- 1h：跑固定回归，区分程序检查、模型裁判、人工判分与任务完成；报告成本/延迟的真实样本和限制。
- 1h：完成短 PRD：问题、用户、核心流程、范围、指标、失败策略和迭代优先级。
- 1h：录制 3–5 分钟演示，整理 README 与两种简历项目表述（产品/工程），只写实际完成工作。
- 0.5h：练习解释 RAG、记忆、评测、Agent 取舍及一个失败案例。
- 0.5h：缓冲、清理公开材料和最终提交。

验收：别人能按 README 启动，能看懂实际结果与局限；你能不靠照读解释一次完整流程，并指出自己独立修改的位置。交付：仓库首页、安装/运行说明、PRD、评测报告、演示、简历条目。

## Github 留痕与优先级规则

每块提交代码、依赖版本、运行命令、题目/标准、实际结果、失败与修复、自己的解释。主线未验收不伪装完成；标清 AI 协助和学生独立部分。公开副本排除密钥、服务器连接信息、原始私密日志和个人配置。

资源或依赖阻塞时：先完成可演示的应用和可信的评测，保留开源项目的最小路径与阻塞记录，再压缩扩展阅读。不会因为安装过许多包就宣称已经掌握。投递时主打一个完整项目与可解释实验，对研究框架诚实写学习/最小实验。
