# 06：从需求到评测，再决定怎样改进 RAG

日期：2026-10-28。AI 协助编写讲义、合成题与评测程序；学习者独立分析待完成。上一块命名会话代码已部署、离线检查通过，真实续聊结果尚未验收，不阻碍开始本块。

## 1. 将产品愿望变成可以检查的需求

“做一个聪明的 AI 助手”无法验收。我们先提出一个待验证的产品假设：学习 AI 的学生需要根据可信资料解释术语、对比工具、继续讨论学习任务。不是已完成的用户调研结论。

本阶段任务：输入问题 → 检索本地资料 → 根据资料生成答案；对资料缺失的情况说明限制。明确知识来源、回答依据与失败原因，为以后增加引用、记忆和工具调用留出接口。

| 用户任务 | 可检查的行为 | 需要的证据 |
|---|---|---|
| 解释一个工具 | 找到对应资料，解释不超出依据 | 检索文档、输出、人工评分 |
| 比较两个工具 | 取回两个必要来源，分别说明 | 相关文档覆盖率、事实核对 |
| 换一种说法提问 | 能找到语义相关的资料 | 同义改写题的检索结果 |
| 问资料之外的事 | 不编造来源或虚假事实 | 无答案题上的检索与最终回复 |
| 继续之前的讨论 | 恢复正确会话，避免混入另一会话 | 会话恢复记录与请求消息 |

这就是 PRD 的起点：目标用户、场景、范围、验收标准。MVP 先验证最重要的任务；目前不做任意联网代理或模型训练。样本量小，暂不写“达到 95% 准确率”之类无依据目标。

## 2. RAG 的两段失败必须分开

RAG = Retrieval-Augmented Generation，检索增强生成。它通常先从外部知识中找材料，再将材料放入模型上下文生成答案。当前 day2 已有这个基本结构，但使用关键词检索，还没有向量数据库、语义检索或引用系统。

检索失败：需要的材料没被找到。生成失败：材料已经提供，模型仍然漏答、误解或编造。提高模型能力不能保证修复检索失败；盲目增加资料也可能带来噪声。

后续 Embedding 把文本表示为向量，以向量相似度寻找语义相关内容；相似度不等于事实正确或文档权威。向量检索也有失败，需要与关键词基线比较，必要时混合检索、重排。当前没有实现这些组件。

## 3. 什么是好的评测题

一个用例包括输入、期望结果或评分标准、类别和数据来源。本节 datasets/retrieval_dev.json 有 10 道 AI 辅助构造的开发题：直接关键词、同义表达、多来源、无答案。它不是用户调研数据，也不是隐藏测试集。

期望相关文档由题目语义人工设定，不能直接拿程序输出当标准答案。比如“记忆”本身有歧义，本练习约定 Mem0 和 OpenViking 两条都相关；真实产品可能应该先澄清，标签依赖任务约定。

Langfuse 的 Dataset 可以管理输入与期望输出，Experiment 对固定数据运行应用并评估结果。我们先理解数据与指标，再接入平台：[官方数据集说明](https://langfuse.com/docs/evaluation/experiments/datasets)、[评测概念](https://langfuse.com/docs/evaluation/core-concepts)。

## 4. 指标怎么计算

设相关文档集合为 R，返回集合为 S：

- Recall@k = |R ∩ S| / |R|：应找的资料找到了多少？
- Precision@k = |R ∩ S| / |S|：拿来的资料有多少相关？本练习无返回时记 0。
- 完整覆盖率：有答案的问题中，所有相关资料都被找回的比例。
- 无答案误检率：无答案的问题中，仍返回资料的比例。这不是最终回答的幻觉率。

如果需要两份材料，只找回一份正确材料，Recall=1/2，Precision=1/1。再多拿来两份无关材料，Recall仍为1/2，Precision变成1/3。所以 top_k 越大不一定越好。

本程序对有答案题逐题计算，再取宏平均。无答案题单独报告，避免把“不返回”与“找对资料”混为一个指标。它只评检索，不评模型生成、不调用 API、没有 token 成本。它调用 app.lookup，并使用独立固定配置，避免个人 config 改动污染对照。

## 5. 开发集、测试集与过拟合

开发集用于看错误、调关键词和参数。最终测试集用于较少次数地检验改进能否推广；如果不断根据测试答案改系统，它就逐渐变成开发集。给每道已知题都加一个特殊关键词，分数会变高，但不一定能处理新表达。

模型训练时还会用训练集更新权重；当前只在改应用逻辑，没有训练模型。无论训练还是检索调参，同一问题的轻微改写跨越开发/测试边界，都可能让结果过于乐观。后续应按任务或来源分组，并由独立人员补充新题。

## 6. 本次实践与基线

在项目目录执行：

```bash
python evaluate_retrieval.py --top-k 1
python evaluate_retrieval.py --top-k 2
```

控制变量：相同知识、问题、标签和检索算法，只改变 top_k。报告默认写入已忽略的 logs/eval 下。公开 reports 中保留助教运行产生的合成开发集基线，不代表学习者操作或真实用户质量。

重点看三类失败：同义表达没有关键词所以没检索到；多来源任务被 top_k 截断；问题虽然含关键词，却问的是资料中没有的内容。下一步选择一个失败类别改进，并同时检查其他类别是否退步。

助教实测（10 道合成开发题，其中 8 道有答案、2 道无答案）：

| 指标 | top_k=1 | top_k=2 |
|---|---|---|
| 有答案题宏平均 Recall | 62.5% | 75.0% |
| 有答案题宏平均 Precision | 75.0% | 75.0% |
| 完整覆盖率 | 50.0% | 75.0% |
| 无答案误检率 | 50.0% | 50.0% |

增大 k 修复了两道多来源题的截断，没有修复同义词和“关键词命中但内容不足”。Precision 未下降只是这批样本的结果，不代表更多文档永远没有噪声。助教运行与学习者运行分开记；指标测试覆盖部分召回、无关文档和空分母处理。

建议本块 90 分钟：原理与 PRD 25 分钟；读数据和跑对照 20 分钟；读 evaluate_retrieval.py 20 分钟；分析错误与提出改进 25 分钟。无需逐条截图确认命令；将结论、修改和结果一起记录。

后续还要评价生成正确性、依据一致性、任务完成、延迟和成本。不能把本次检索分数当作整个 AI 应用的准确率，也不能用 10 道合成题证明岗位熟练度。
