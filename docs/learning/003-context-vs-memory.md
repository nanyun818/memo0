# 03：会话上下文与长期记忆

日期：2026-10-27。

状态：同会话追问与新进程对照已验证，学习者已正确解释恢复旧历史的基本作用；持久化代码实践和其余独立挑战继续完成。

## 要解决的问题

模型为什么在同一次聊天里能接着聊？退出程序重新开始后，它还知道前面的内容吗？日志已经写到磁盘，为什么不等于模型下次自动记住？

## 代码中的原因

day2.py 的 --chat 用 history 列表保存当前进程中的消息。每一轮把这些消息加入 messages 再发给 API。退出后列表随进程结束；重新启动时新建空列表。程序会写日志，但没有读取日志来恢复历史。

长期记忆需要应用明确保存、检索并把相关内容放回请求。后续 Mem0 模块会实现这一点；仅安装库或写了日志不会自动形成可靠的长期记忆。

## 实验 A：同一会话

先进入项目、激活虚拟环境，确保当前终端已有 DEEPSEEK_API_KEY。运行：

```bash
python day2.py --chat --no-context
```

依次输入以下三行，每行等待模型回复后继续：

```text
这次练习的项目代号是蓝鲸，请记住。
刚才的项目代号是什么？
/exit
```

--no-context 不提供本地知识库资料，但当前进程的 history 仍会被发送。预期模型可根据前文回答；实际回答以运行结果为准。

## 实验 B：新会话

重新运行同一条 --chat 命令，只问：

```text
刚才的项目代号是什么？
```

新会话没有提供旧代号。若模型猜中，也不能据此判定存在跨会话记忆。可换一个随机代号复核。

|---|---|---|---|---|
| 第一轮告知项目代号 | 模型回复确认 | 0 | 73 / 17 | 0.725 |

学习者提出：“第二个对话没有上一个对话的记忆，所以无法回复”，这一点符合观察；同时询问是否因为“不在一个项目里”。两次实际位于同一个项目，真正变化的是进程重启后没有恢复旧历史。

## 背后原理：目录、进程、请求、模型

1. **项目目录**保存代码和文件。本次两次运行的目录相同。目录相同不会让外部模型自动读取其中的文件。
2. **Python 进程**是一次程序运行。本程序启动 --chat 后执行 `history = []`，在内存里新建历史列表。每轮成功后把用户消息和助手回复追加到列表。退出后，该进程内存不再由新运行的程序使用。
3. **API 请求**携带本次 messages。build_messages 把 system、history 和当前 user 消息组合起来。第二轮带上历史，因此模型可以参考代号；新进程的 history 为空，因此 messages 没有旧代号。
4. **模型推理**根据当前提供的 token 上下文与已训练的参数生成回答。本程序没有训练步骤，这次聊天不会因一句“记住”更新模型权重。API Key 用于请求认证，不负责把不同请求自动关联为这个应用的一段对话。

DeepSeek 官方明确说明，本课所用的 /chat/completions 是无状态接口，多轮对话需要应用每次自行拼接并传入历史消息。这里描述的是对话上下文的接口行为，不把它扩展成对服务方日志留存政策的判断。[官方多轮对话说明](https://api-docs.deepseek.com/guides/multi_round_chat/)

下面是省略 system、参考资料和 JSON 包装后的示意消息，不是完整抓包：

```python
# 同会话第二轮
messages = [
    {"role": "user", "content": "项目代号是蓝鲸"},
    {"role": "assistant", "content": "好的"},
    {"role": "user", "content": "刚才的项目代号是什么？"},
]

# 重启后的第一轮
messages = [
    {"role": "user", "content": "刚才的项目代号是什么？"},
]
```

日志文件虽保留在磁盘，本程序没有把它读回 history。因此“写了日志”和“恢复会话”是两件事。同样的代码如果增加“保存并按 session_id 加载历史”，可以恢复旧会话；若增加“按 user_id 检索相关记忆并放入请求”，可以支持跨会话长期记忆。后者是之后 Mem0 模块要实践的方向。

这种设计让应用明确决定哪些会话可继续、哪些信息要携带，以及上下文长度如何控制。无状态接口不妨碍应用提供有状态的聊天体验。

## 学习者的解释与反馈

2026-10-27，学习者回答：“应该是可以的，加载旧的历史，模型可以读取并且回答原来的代号。”

该回答正确抓住恢复历史可以支持续聊的基本因果。进一步明确：由应用读取磁盘文件，将加载的历史加入本次 messages 再发送给模型；模型不会自动读取项目中的文件。仅把文件读入变量、但不传入请求，仍然不能让模型使用它。

本次确认的是基本概念理解，不把它等同于已经独立实现会话持久化。下一步做保存、结束进程、新进程加载的离线练习。
