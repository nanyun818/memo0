# 09：让模型当裁判，先检查裁判能否识别明显错误

日期：2026-10-30。状态：AI 助教准备代码、六条合成答案与参考标签；离线框架验证通过；学习者真实裁判实验与独立核对待完成。六条答案不是新生成的真实模型表现。

## 从上轮结果继续

上一轮普通指令 4/5、强调依据指令 5/5，唯一失败是引用字段约定。程序尚不能识别“Mem0 是咖啡机”这样的语义错误。本节增加 llm-rubric，把问题、资料、候选答案和评分标准发给裁判模型。

这是一次独立的评分请求。与上轮生成答案使用相同型号 DeepSeek，角色与请求不同，不意味着裁判更聪明或独立无偏；相同模型可能共享盲点。更换裁判也仍需要核对。

## 先限定一个评分维度

本节只判“依据一致性”：答案中的实质性事实是否被给定资料支持？若资料不足，准确承认未知可以通过；出现无依据事实或保证则不通过。

这不同于任务完成度。问题问如何隔离依赖，但检索资料为空，回答“资料不足”可以通过依据一致性，仍然没有完成用户任务。也不同于开放世界事实正确性：某句话即使符合外部常识，没有给定资料支持，也可能在本维度失败。

Rubric 是评分标准。本节要求裁判返回 pass（通过与否）、score（本节严格 0 或 1）、reason（中文判分原因）。与候选答案自身的 supported 字段分开，裁判要读正文，而不是相信候选者自称有依据。

## 六个固定样例

| 编号 | 候选答案的要点 | 助教建议的依据一致性标签 |
|---|---|---|
| j01 | Mem0 帮助保存、检索长期记忆 | 通过 |
| j02 | Mem0 是家用咖啡机 | 不通过 |
| j03 | 资料不含收入，无法确定 | 通过 |
| j04 | 先说没有收入资料，又声称收入100万元 | 不通过 |
| j05 | 无资料，无法回答依赖隔离方法 | 通过；任务完成度另测 |
| j06 | 正确介绍记忆用途，又保证所有回答永远正确 | 不通过 |

这些是 AI 助教构造的校准样例及建议标签，不是人类专家标注集。学习者应核对并指出不同意见；少量明显正反例只验证流程和基本辨别力。真实校准还需独立人工标注、难例、更多样本和分歧分析，不能凭六条一致就宣布裁判可靠。

## 操作

沿用私人启动指南连接服务器，进入项目并激活环境，进入 evals/promptfoo。无需安装新框架。

```bash
npm run judge-preview
```

预览不调用 API，显示六条答案、旧程序规则结果和助教参考标签。六条都会通过旧规则，说明旧规则覆盖的范围有限。参考标签仅在 metadata 内，不插入裁判 Prompt，避免把标准结果泄露给裁判。

真实运行需要当前终端已有 DEEPSEEK_API_KEY；若未设置，先单独执行隐藏输入：

```bash
read -rsp '输入 DeepSeek 密钥后回车：' DEEPSEEK_API_KEY
```

按回车结束输入，再执行：

```bash
export DEEPSEEK_API_KEY
npm run judge
```

被测 provider 是 echo，只回显固定答案；llm-rubric 的 provider 显式指定 deepseek:deepseek-flash 作为裁判。正常情况下 6 条答案产生 6 次付费裁判请求，没有重新生成答案。配置 maxRetries=0、每次最多500输出token、temperature=0、thinking disabled；仍不保证完全可重复，错误不应盲目重跑。运行禁用缓存，重复实验会再次产生用量。

执行结束后读中文汇总：

```bash
npm run judge-report
```

它比较裁判判分与助教建议标签，列出分歧；缺失或出错判分不当作有效失败答案。有效判分数和一致数分别报告，不把错误自动算正确，也不把六条合成样例的一致性称为线上准确率。

## 网页怎么读

已有网页刷新后，在实验下拉框选择 `Judge calibration - six synthetic answers, evidence consistency only`。

输出列仍显示 echo，因为答案由固定样例回显；真正的裁判调用在断言里。点候选答案旁的放大镜，找 EvidenceConsistency（依据一致性）和中文 reason；FormatAndLabels 是原程序规则。

j02/j04/j06 如果被裁判识别，应该显示 FAIL。这一次出现 FAIL 是预期：我们故意拿错误答案测试评分器，不是希望错误答案全部 PASS。最终要比较“该失败的是否失败、该通过的是否通过”。整体通过率低不等于裁判差。

程序检查通过、裁判不通过时，合并分数可能是 0.5（两项均值），整条仍 FAIL。判分一致性按 llm-rubric 组件的 pass，与 metadata 的参考标签比较，不使用总平均分替代裁判结论。

## 阅读代码与后续工作

- judge.yaml：裁判模型配置、评分标准；最先读这一份。
- judge-cases.json：问题、资料、固定答案与助教参考标签。
- read_judge_report.py：区分有效判分、错误和分歧。
- run.sh 的 judge 分支：串行运行并保存 JSON/HTML。

本次助教完成默认预览、YAML 配置校验，以及用固定假裁判替换真实裁判的接口检查：6 条规则通过、6 条固定假裁判失败、0 执行错误。假裁判仅验证框架能加载和保存判分，未验证 DeepSeek 裁判质量，也未产生付费请求。

完成本节后，下一步把标准移到 DeepEval 的 Python 测试，再与应用回归结合。每次先保留失败案例和判分依据，避免反复修改标准迎合某个结果。

官方依据：[promptfoo llm-rubric](https://www.promptfoo.dev/docs/configuration/expected-outputs/model-graded/llm-rubric/) 支持显式裁判 provider、中文标准和自定义评分提示。本节不依赖默认裁判选择，以免误调用其他服务。
